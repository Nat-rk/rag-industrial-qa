# 小白版：这套问答系统是怎么运转的

> 写给"能看懂零散 Python，但一看多文件项目就晕"的读者。
> 目标：读完你能说出每个文件负责什么、数据在它们之间怎么流动、出了问题该先看哪。

---

## 0. 先看一张图

```
用户提问
   │
   ▼
main.py ──①选策略──> retrieval/bm25.py   或   retrieval/hybrid.py
   │                        │
   │                        ▼  30 个句子
   │                  retrieval/backfill.py   ← 句子换成"父块"，顺带去重、不够 10 个就扩大范围
   │                        │
   │                        ▼  30 个父块
   │                  retrieval/reranker.py   ← 用 rerank-pro 重新排序，取前 10
   │                        │
   │                        ▼  10 个父块
   │                  qa/context_builder.py   ← 拼成带 [Source n] 的上下文
   │                        │
   │                        ▼  一段长文本
   │                  qa/generator.py         ← 调 glm-4.5-flash 生成答案
   │                        │
   │                        ▼  答案文本
   │                  qa/citation.py          ← 把 [Source 2] 换成"apply.pdf 第 8 页"
   ▼
终端打印：过程 + 答案 + 来源
```

一句话记住这条链：**问题 → 句子 → 父块 → 重排 → 上下文 → 答案 → 引用。**

为什么中间要"句子→父块"绕一下？打个比方：
- **句子**像"目录卡片"，每张只写一句话，好翻、好找；
- **父块**像"整页复印件"，内容全，但整页拿去比对太笨重。
- 所以：**用卡片找位置，找到后把整页复印给老师（LLM）看。**

## 1. `config.py`：全项目的"遥控器面板"

**它解决什么**：把"用哪个模型、取多少条、开不开 rerank"这些数字从代码里抽出来，改参数不用翻业务代码。

```python
RETRIEVAL_MODE = "bm25"     # 换成 "hybrid" 就切策略
TOP_K_UNITS = 30            # 先召多少句子
BACKFILL_TARGET = 30        # 回填多少个父块（给 rerank 挑）
DELIVER_K = 10              # 最终交给 LLM 几块
LLM_MODEL = "glm-4.5-flash"
```

**你大概率会改的**：`RETRIEVAL_MODE`（切策略）、`DELIVER_K`（上下文块数）、`LLM_MODEL`。
**别乱改的**：`RRF_K=60`、`STEPS=(30,60,120,240)`——这些是实验里验过的，改了结果不可比。

---

## 2. `retrieval/store.py`：唯一的数据入口

**它解决什么**：项目里有两份数据——`out/parents.json`（父块正文）和 `storage/docstore.json`（父块的元数据：文件名、页码、是否目录页）。这个文件把它们合成一个 `Parent` 对象，别处就不用关心 JSON 长什么样。

```python
@dataclass
class Parent:
    id: str        # 父块 ID
    page: int      # 页码
    kind: str      # section / table / toc
    section: str   # 章节名
    text: str      # 正文
    chars: int
    file_name: str # 引用时要显示的文件名
```

**输入**：无（自己去读文件）。**输出**：`load_parents()` 给 278 个父块，`load_units()` 给 1679 个句子。
**注意**：`docstore.json` 套了三层壳（`docstore/data/<id>/__data__`，而 `__data__` 有时还是字符串），所以里面有个 `_docstore_metadata()` 专门拆壳——这是踩过的坑。

---

## 3. `retrieval/bm25.py`：关键词检索

**它解决什么**：把 1679 个句子做成"倒排索引"（词 → 出现在哪些句子），按词频打分。它的强项是**精确编号**（`3-22`、`8-10`），弱项是"换个说法就找不到"。

```python
language = sorted(set(STOPWORDS_EN) | set(config.EXTRA_STOPWORDS))  # 33 + 12 = 45 个停用词
retriever = BM25Retriever.from_defaults(nodes=unit_nodes, similarity_top_k=240, language=language)
```

为什么要 45 个停用词？因为默认只有 33 个，`what / which / does` 这些疑问词没被过滤，会把"问题里的废话"当成关键词去匹配（实验里 Q2 就因为 `does` 排错，加词后从第 3 名升到第 1）。

**输入**：问题字符串。**输出**：`[Hit(句子id, 父块id, 页码, 触发句, 分数)]`。

---

## 4. `retrieval/hybrid.py`：把两种检索"投票合并"

**它解决什么**：BM25 和向量各自排出 50 名，用 RRF 合并成一个榜单——**只按名次投票，不看原始分数**（因为一个无量纲、一个是 exp(-距离)，没法相加）。

```python
score = 1 / (RRF_K + rank)      # 第 1 名得 1/61，第 2 名得 1/62……
两路分数相加，同一句子出现两次就加两次
```

**为什么必须按名次**：向量分数 0.77 和 BM25 分数 9.2 之间没有可比性，直接相加等于让 BM25 说了算。

**输入**：问题。**输出**：融合后的 `[Hit]`，取前 n。
**里面还有个 `DenseRetriever`**：负责调 embedding-3 把问题变成 1024 维向量，去 Chroma 里找最近的句子。查询向量只放内存，不落盘。

---

## 5. `retrieval/backfill.py`：句子 → 父块，顺便解决"不够 10 个"

**它解决什么**：检索单位是句子，但喂给 LLM 的必须是父块。这一步把命中的句子换成它所属的父块，并**按父块去重**（同一页被 5 个句子命中，只算 1 个父块）。

**关键规则**（`adaptive_backfill`）：
1. 先取 30 个句子 → 回填 → 去重；
2. 如果不同父块 < 10 个，就扩到 60、120、240 个句子再来一遍；
3. 够了 / 句子用完了 / 到上限就停；
4. **不补假数据**，不足 10 个就返回真实数量。

**为什么需要它**：一张大表格（比如 2071 字的 Table 3）会一口气吃掉 30 个句子里的 8 个，去重后只剩 4 个父块——上一轮 BM25 就交付不足。现在会自动扩到 60 个候选，补满 10 个。

**输入**：`[Hit]` + 父块字典。**输出**：`(父块列表, 每轮轨迹)`，轨迹长这样：`[{"candidates":30,"returned":30,"parents":10}]`。

---

## 6. `retrieval/reranker.py`：重排（可选，但默认开）

**它解决什么**：检索是"粗筛"，rerank 是"精排"。它把问题和 30 个父块正文一起交给 `rerank-pro`，逐对打分，再取前 10。

```python
try:
    return rerank_documents(...)          # 正常
except RerankError as e:
    return candidates[:top_k], {"degraded": True, "error": str(e)}   # 失败就保持原顺序
```

**三条硬规则**：
- 输入必须是**父块正文**，不是句子；
- 只改顺序，不加候选、不删候选（除了截到 10）；
- **失败不能崩**——退回原顺序并打上 `degraded` 标记，让调用方知道"这次没有重排"。

**输入**：问题 + 30 个父块。**输出**：前 10 个父块 + `{"elapsed":..., "degraded": False}`。

---

## 7. `qa/context_builder.py`：把父块拼成"老师能读的卷子"

**它解决什么**：LLM 只能看到你给它的文字。如果只把正文糊在一起，模型就不知道哪句话来自哪一页，引用必然瞎编。

所以每块都带上身份证：

```
[Source 1]
File: apply.pdf
Page: 44
Parent ID: 1a2b3c4d
Section: 2.10.1 ...

<正文>
```

**两个保险**：单块最多 2600 字（最长父块 2607，刚好不截断），总量最多 24000 字。

**输入**：10 个父块。**输出**：`(context 字符串, sources 列表)`——后者是引用模块的"底账"。

---

## 8. `qa/generator.py`：真正说话的那一步

**它解决什么**：拼 Prompt + 调 LLM。Prompt 里写死七条约束，最重要的是：

1. 只依据上下文回答，不许拿"模型自己的知识"冒充文档；
2. 资料不足要明说"文档中没有足够信息"；
3. 参数名、选项值要**逐字照抄**（`[9] Positioning` 不能写成"第九项"）；
4. 不同来源冲突要指出来，不许自己选一个；
5. 每个结论后面标 `[Source n]`。

**输入**：问题 + context。**输出**：`(答案文本, token 用量, 耗时)`。
**注意**：LLM 调用失败会抛 `RuntimeError`，`main.py` 会接住并显示"（生成失败：…）"，不会让整个程序崩掉。

---

## 9. `qa/citation.py`：把 `[Source 2]` 变成"第 8 页"

**它解决什么**：模型只会写 `[Source 2]`，用户要看的是"apply.pdf 第 8 页"。这个模块用正则把编号抽出来，再去 `sources` 底账里查页码。

```python
SOURCE_RE = r"\[?Source\s*(\d+)\]?"     # 兼容 "[Source 2]" 和裸写的 "Source 2"
```

**三条规则**：
- 只映射"模型真的引用过"的编号——**不许凭空加引用**；
- 编号越界或不存在，就报"未标注"，不猜；
- 模型一个引用都没写时，如实说"模型未标注来源"，并列出可人工核对的片段（不伪造）。

**输入**：答案文本 + sources。**输出**：`[(页码, 文件名, section), ...]`。

---

## 10. `main.py`：唯一需要你记住的入口

它只做"串流程"，不写业务细节：

```python
parents = load_parents()                 # 数据
retriever = build_retriever(mode, units) # ① 选策略
candidates, trace = adaptive_backfill(...)   # ②③ 召回 + 回填
picked, rerank_info = rerank_candidates(...) # ④ 重排
context, sources = build_context(picked)     # ⑤ 上下文
answer_text, usage, _ = llm_answer(...)      # ⑥ 生成
used, marked = build_citations(answer_text, sources)  # ⑦ 引用
show(result)                                  # ⑧ 打印
```

`ask()` 返回一个大字典，里面什么都有（候选、轨迹、rerank 结果、上下文、答案、引用、耗时）。测试脚本就是复用它，所以一次问答和批量评测走的是**同一套代码**，不会出现"评测能过、手动跑不通"。

## 11. 一次真实问答，逐段看

```
问题：参数 3-22 和 3-23 是干什么的？
① 选策略：bm25
② 召回：30 个句子（含 "the gear ratio is set by the master scaling in parameter 3-22…"）
③ 回填：30 个父块，去重后 10 个 → 不用扩展
④ rerank：10 个里把 p11（定义句）排到第 1
⑤ 上下文：10 块，每块带 [Source n] + 页码
⑥ 生成：glm-4.5-flash 写出"3-22 分子 / 3-23 分母，用分数避免舍入误差"
⑦ 引用：[Source 2] → apply.pdf 第 11 页
⑧ 打印：过程 + 答案 + 来源
```

## 12. 出问题先看哪里（排错表）

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 报"缺少 ZHIPU_API_KEY" | `retrieval/store.py` 的 `api_key()` | 环境变量没设 |
| 检索结果全是目录页 | `retrieval/store.py` 的 `load_parents()` | 目录父块下没有句子，理论上不会出现；若出现说明数据被换过 |
| 交付不足 10 个 | `out/` 里没有，看 `trace` | 候选扩到 240 还不够，说明该问题确实没有 10 个相关块 |
| 答案说"文档中没有"但文档里有 | `qa_cases.json` 的 `pages` + `context` | 检索没命中，或 rerank 把相关块挤出前 10 |
| 引用页码对不上 | `qa/citation.py` 的映射 + `sources` | 模型写了不存在的编号，或上下文被截断 |
| rerank 报错但程序没停 | 打印里的 `⚠ rerank 已降级` | 额度/网络问题，已自动退回原顺序 |
| 中文问、英文文档答不上 | 策略 | BM25 倒排是英文 token，中文提问请用 hybrid |

## 13. 三个"为什么这样设计"

1. **为什么不把句子直接给 LLM？**
   句子太碎，表格行离开表头就没有意义（Q5 的 Control Word 表被切成 5 块，单块只有 bit 0–2）。父块是"能独立读懂"的最小单位。

2. **为什么 rerank 放在回填之后，而不是句子层？**
   因为最终要给 LLM 的是父块；在句子层重排还要再做一次去重，且句子分数无法代表整块的相关性。一次调用 30 个块，比 30 次调用句子便宜。

3. **为什么两种策略共用一个 `reranker.py` / `context_builder.py` / `generator.py`？**
   否则"两种方案的差异"里会混进"两套 Prompt 的差异"，实验就不可比了。**控制变量**是这套代码最值钱的地方。
