# 小白版：这套问答系统是怎么运转的

> 写给"能看懂零散 Python，但一看多文件项目就晕"的读者。
> 目标：读完你能说出每个文件负责什么、数据在它们之间怎么流动、出了问题该先看哪。

---

## 0. 先看一张图

```
                    ┌──────────── HTTP 客户端（curl / Swagger / 前端）
                    │
                    ▼
              api/app.py  create_app + lifespan
                    │  ├─ 启动：RagEngine.initialize()（读数据、建检索器、预热）
                    │  ├─ 请求：api/routes.py → 校验 → 拿锁 → engine.ask()
                    │  └─ 关闭：engine.close()
                    │
用户提问 ────────────┤（CLI：python main.py "…"）
   │                │
   ▼                ▼
main.py ──①选策略──> qa/pipeline.py ──> retrieval/bm25.py   或   retrieval/hybrid.py
   │                        │
   │                        ▼  30 个句子
   │                  retrieval/backfill.py   ← 句子换成"父块"，顺带去重、不够 10 个就扩大范围
   │                        │
   │                        ▼  30 个父块
   │                  retrieval/reranker.py   ← 用 rerank-pro 重新排序，取前 10
   │                        │
   │                        ▼  10 个父块
   │                  qa/context_builder.py   ← 拼成带 [Source n] 的上下文
   │                        │
   │                        ▼  一段长文本
   │                  qa/generator.py         ← 调 glm-4.5-flash 生成答案
   │                        │
   │                        ▼  答案文本
   │                  qa/citation.py          ← 把 [Source 2] 换成"apply.pdf 第 8 页"
   ▼
终端打印 / JSON 响应：过程 + 答案 + 来源
```

两条入口共用 `qa/pipeline.py`：CLI 每次执行都重新加载数据；HTTP 服务在启动时加载一次，
之后每个请求复用同一个 `RagEngine`。

一句话记住这条链：**问题 → 句子 → 父块 → 重排 → 上下文 → 答案 → 引用。**

为什么中间要"句子→父块"绕一下？打个比方：
- **句子**像"目录卡片"，每张只写一句话，好翻、好找；
- **父块**像"整页复印件"，内容全，但整页拿去比对太笨重。
- 所以：**用卡片找位置，找到后把整页复印给老师（LLM）看。**

## 1. `settings.py`：全项目的"遥控器面板"

**它解决什么**：把"用哪个模型、取多少条、开不开 rerank"这些数字从代码里抽出来，改参数不用翻业务代码。

```python
RETRIEVAL_MODE = "bm25"     # 换成 "hybrid" 就切策略
STEPS = (30, 60, 120, 240)  # 自适应扩展的候选句子数
BACKFILL_TARGET = 30        # 回填多少个父块（给 rerank 挑）
DELIVER_K = 10              # 最终交给 LLM 几块
LLM_MODEL = "glm-4.5-flash"
```

**分工**：数值真源只有 `settings.py` 的 `Settings`（frozen dataclass，构造即校验，可用 `RAG_*` 环境变量覆盖，`Settings.from_env()` 是唯一读环境变量的入口）。S1 期间 `config.py` 曾作为别名层过渡，S3 已删除——现在所有组件都通过参数接收 Settings 里的值，不再 import 任何全局配置。配置写错时启动就抛 `ConfigError`。

**你大概率会改的**：`RETRIEVAL_MODE`（切策略）、`DELIVER_K`（上下文块数）、`LLM_MODEL`。
**别乱改的**：`RRF_K=60`、`STEPS=(30,60,120,240)`——这些是实验里验过的，改了结果不可比。

**配套的两个小文件**：`errors.py` 定义 `ConfigError / DataError / LLMError / RerankError`（都继承 `RagError → RuntimeError`，退出码由入口决定）；`logging_setup.py` 负责"日志配一次 + 每次问答一个 trace_id"，业务代码只 `getLogger(__name__)`。

## 2. `retrieval/store.py`：唯一的数据入口

**它解决什么**：项目里有两份数据——`out/parents.json`（父块正文）和 `storage/docstore.json`（父块的元数据：文件名、页码、是否目录页）。这个文件把它们合成一个 `Parent` 对象，别处就不用关心 JSON 长什么样。

```python
@dataclass
class Parent:
    id: str        # 父块 ID
    page: int      # 页码
    kind: str      # section / table / toc
    section: str   # 章节名
    text: str      # 正文
    chars: int
    file_name: str # 引用时要显示的文件名
```

**输入**：无（自己去读文件）。**输出**：`load_parents()` 给 278 个父块，`load_units()` 给 1679 个句子。
**注意**：`docstore.json` 套了三层壳（`docstore/data/<id>/__data__`，而 `__data__` 有时还是字符串），所以里面有个 `_docstore_metadata()` 专门拆壳——这是踩过的坑。

## 3. `retrieval/bm25.py`：关键词检索

**它解决什么**：把 1679 个句子做成"倒排索引"（词 → 出现在哪些句子），按词频打分。它的强项是**精确编号**（`3-22`、`8-10`），弱项是"换个说法就找不到"。

```python
language = sorted(set(STOPWORDS_EN) | set(extra_stopwords))  # 33 + 12 = 45 个停用词（S3 起由 Settings 传入）
retriever = BM25Retriever.from_defaults(nodes=unit_nodes, similarity_top_k=240, language=language)
```

为什么要 45 个停用词？因为默认只有 33 个，`what / which / does` 这些疑问词没被过滤，会把"问题里的废话"当成关键词去匹配（实验里 Q2 就因为 `does` 排错，加词后从第 3 名升到第 1）。

**输入**：问题字符串。**输出**：`[Hit(句子id, 父块id, 页码, 触发句, 分数)]`。

---

## 4. `retrieval/hybrid.py`：把两种检索"投票合并"

**它解决什么**：BM25 和向量各自排出 50 名，用 RRF 合并成一个榜单——**只按名次投票，不看原始分数**（因为一个无量纲、一个是 exp(-距离)，没法相加）。

```python
score = 1 / (RRF_K + rank)      # 第 1 名得 1/61，第 2 名得 1/62……
两路分数相加，同一句子出现两次就加两次
```

**为什么必须按名次**：向量分数 0.77 和 BM25 分数 9.2 之间没有可比性，直接相加等于让 BM25 说了算。

**输入**：问题。**输出**：融合后的 `[Hit]`，取前 n。
**里面还有个 `DenseRetriever`**：负责调 embedding-3 把问题变成 1024 维向量，去 Chroma 里找最近的句子。查询向量只放内存，不落盘。

---

## 5. `retrieval/backfill.py`：句子 → 父块，顺便解决"不够 10 个"

**它解决什么**：检索单位是句子，但喂给 LLM 的必须是父块。这一步把命中的句子换成它所属的父块，并**按父块去重**（同一页被 5 个句子命中，只算 1 个父块）。

**关键规则**（`adaptive_backfill`）：
1. 先取 30 个句子 → 回填 → 去重；
2. 如果不同父块 < 10 个，就扩到 60、120、240 个句子再来一遍；
3. 够了 / 句子用完了 / 到上限就停；
4. **不补假数据**，不足 10 个就返回真实数量。

**为什么需要它**：一张大表格（比如 2071 字的 Table 3）会一口气吃掉 30 个句子里的 8 个，去重后只剩 4 个父块——上一轮 BM25 就交付不足。现在会自动扩到 60 个候选，补满 10 个。

**输入**：`[Hit]` + 父块字典。**输出**：`(父块列表, 每轮轨迹)`，轨迹长这样：`[{"candidates":30,"returned":30,"parents":10}]`。

---

## 6. `retrieval/reranker.py`：重排（可选，但默认开）

**它解决什么**：检索是"粗筛"，rerank 是"精排"。它把问题和 30 个父块正文一起交给 `rerank-pro`，逐对打分，再取前 10。

```python
try:
    return rerank_documents(...)          # 正常
except RerankError as e:
    return candidates[:top_k], {"degraded": True, "error": str(e)}   # 失败就保持原顺序
```

**三条硬规则**：
- 输入必须是**父块正文**，不是句子；
- 只改顺序，不加候选、不删候选（除了截到 10）；
- **失败不能崩**——退回原顺序并打上 `degraded` 标记，让调用方知道"这次没有重排"。

**输入**：问题 + 30 个父块。**输出**：前 10 个父块 + `{"elapsed":..., "degraded": False}`。

---

## 7. `qa/context_builder.py`：把父块拼成"老师能读的卷子"

**它解决什么**：LLM 只能看到你给它的文字。如果只把正文糊在一起，模型就不知道哪句话来自哪一页，引用必然瞎编。

所以每块都带上身份证：

```
[Source 1]
File: apply.pdf
Page: 44
Parent ID: 1a2b3c4d
Section: 2.10.1 ...

<正文>
```

**两个保险**：单块最多 2600 字（最长父块 2607，刚好不截断），总量最多 24000 字。

**输入**：10 个父块。**输出**：`(context 字符串, sources 列表)`——后者是引用模块的"底账"。

---

## 8. `qa/generator.py`：真正说话的那一步

**它解决什么**：拼 Prompt + 调 LLM。Prompt 里写死七条约束，最重要的是：

1. 只依据上下文回答，不许拿"模型自己的知识"冒充文档；
2. 资料不足要明说"文档中没有足够信息"；
3. 参数名、选项值要**逐字照抄**（`[9] Positioning` 不能写成"第九项"）；
4. 不同来源冲突要指出来，不许自己选一个；
5. 每个结论后面标 `[Source n]`。

**输入**：问题 + context。**输出**：`(答案文本, token 用量, 耗时)`。
**注意**：LLM 调用失败会抛 `RuntimeError`，`main.py` 会接住并显示"（生成失败：…）"，不会让整个程序崩掉。

---

## 9. `qa/citation.py`：把 `[Source 2]` 变成"第 8 页"

**它解决什么**：模型只会写 `[Source 2]`，用户要看的是"apply.pdf 第 8 页"。这个模块用正则把编号抽出来，再去 `sources` 底账里查页码。

```python
SOURCE_RE = r"\[?Source\s*(\d+)\]?"     # 兼容 "[Source 2]" 和裸写的 "Source 2"
```

**三条规则**：
- 只映射"模型真的引用过"的编号——**不许凭空加引用**；
- 编号越界或不存在，就报"未标注"，不猜；
- 模型一个引用都没写时，如实说"模型未标注来源"，并列出可人工核对的片段（不伪造）。

**输入**：答案文本 + sources。**输出**：`[(页码, 文件名, section), ...]`。

## 10. `qa/pipeline.py` 与 `main.py`：编排与入口

**分工**（S2 之后）：

| 文件 | 职责 | 允许做什么 |
|---|---|---|
| `qa/pipeline.py` | 8 步业务流程编排 | 接收 Settings、调用组件、组装 14 键结果；**不读环境变量**、不碰 stdout、不决定退出码 |
| `main.py` | 进程边界 | 解析 argv、惰性建 Settings（`lru_cache`）、配日志、建输出目录、打印、把 `ConfigError` 转成退出码 2 |

`pipeline.run()` 的骨架：

```python
token = logging_setup.begin_trace()          # 每次问答一个 trace_id
try:
    parents = load_parents(parents_path=s.parents_path, docstore_path=s.docstore_path)
    units   = load_units(units_path=s.units_path)
    retriever = build_retriever(mode or s.retrieval_mode, units, s)   # ①
    candidates, trace = adaptive_backfill(..., target=s.backfill_target, steps=s.steps)  # ②③
    picked, rerank_info = rerank(question, candidates, s.deliver_k, ...)  # ④
    context, sources = build_context(picked, parent_max_chars=..., total_max_chars=...)  # ⑤
    answer_text, usage, _ = llm(question, context, sources, model=s.llm_model, ...)      # ⑥
    used, marked = build_citations(answer_text, sources)                # ⑦
finally:
    logging_setup.end_trace(token)           # 正常/异常/嵌套都会恢复
```

**为什么要有 `rerank_fn` / `llm_fn` 两个参数**：`tests/test_pipeline.py` 用
`mock.patch.object(main, "rerank_candidates")` 避免联网。如果 pipeline 直接调用
自己 import 进来的函数，patch 会静默失效——测试就变成"假通过"。所以 `main.ask()`
每次都把模块属性传进来，pipeline 只按参数调用。

`ask()` 返回的大字典（14 个键）里什么都有（候选、轨迹、rerank 结果、上下文、答案、
引用、耗时）。测试脚本就是复用它，所以一次问答和批量评测走的是**同一套代码**，
不会出现"评测能过、手动跑不通"。

## 10.5 `service/engine.py`：把“每次重来”变成“启动一次”

**它解决什么**：命令行每次运行都要重新读约 312 ms 数据、重建数秒的 BM25 索引；服务化以后每个请求都这样付不起。`RagEngine` 在 `initialize()` 里把 parents / units / 检索器建好并**持有**，之后 `ask()` 直接把这三样传给 `qa/pipeline.py` 的 `run()`——检索逻辑一行没改，只是不再重复构建。

```python
from service.engine import RagEngine
from settings import Settings

engine = RagEngine(Settings.from_env())
engine.initialize()      # load_parents → load_units → build_retriever →（hybrid）prewarm
engine.ask("……")         # 复用上面的对象，仍然走同一个 pipeline.run()
engine.close()           # 关闭自己创建的 Chroma client；closed 是终态
```

**三个状态**：`new`（只拿到 Settings，不碰磁盘）→ `ready`（资源就绪）→ `closed`（已释放，不能再 `initialize()` / `ask()`）。`initialize()` 失败会清理半成品并退回 `new`；重复 `initialize()` 是空操作；`close()` 幂等，且清理异常不会覆盖初始化异常。

**一个约定**：一个数据目录只允许一个同时存活的 Engine——chromadb 按路径缓存 System，`close()` 会连同路径的另一个一起停掉，所以隔离测试必须用不同目录。

**它不做什么**：不读环境变量、不解析命令行、不依赖 `main.settings()` 那个 CLI 单例、不管 HTTP 状态码、不做多轮会话。

## 10.6 `api/`：把问答包成 HTTP 接口（S4）

**它解决什么**：让别的程序（curl、Swagger、将来的前端）能通过 HTTP 提问，而不是只能在终端敲命令。它**不实现**检索或生成——所有业务都在 `service/engine.py` → `qa/pipeline.py` 里。

| 文件 | 职责 |
|---|---|
| `api/app.py` | `create_app(settings, *, engine_factory=RagEngine)` 造 FastAPI 应用；`lifespan` 里 `engine_factory` → `api_key()` 预检 → `engine.initialize()` → 存进 `app.state`；退出时 `engine.close()`；初始化失败时先清理再抛出 |
| `api/main.py` | uvicorn 入口：`app = create_app(Settings.from_env())`，命令是 `uvicorn api.main:app --workers 1` |
| `api/routes.py` | `POST /ask`、`GET /healthz`、`GET /readyz`；`/ask` 是同步 `def`，用 `app.state.ask_lock` 串行 |
| `api/schemas.py` | `AskRequest`（1–2000 字、禁止多余字段）、`AskResponse`（14 键；`parent` 从 dataclass 展开成 `ParentOut`）、`SourceOut`（含 `chars`）、`CitationOut`（**不含 `chars`**，对应 `build_citations()` 的真实形状）、`Timing` |
| `api/errors.py` | `EngineNotReady` + 异常 → 状态码映射 + 统一外壳 `{"error":{"code","message","trace_id"}}`；422 由 FastAPI 处理 |

**资源生命周期**：应用启动 → 建 Engine → `initialize()` → 存 `app.state` → 多个请求复用 → 关闭时 `close()`。API 层只管应用级生命周期，Engine 自己管内部资源（父块、句子、检索器、Chroma 客户端）。

**并发模型**：`/ask` 同步路由跑在 Starlette 的线程池里；`app.state.ask_lock`（`threading.Lock`）保证同一进程内一次只有一个 `engine.ask()`。`/healthz`、`/readyz` 是 `async def`，直接跑在事件循环里，不会被问答占满线程池。**不**宣称 Engine 本身线程安全，也**不**支持多 worker 全局串行。

**异常映射**：`ConfigError` → 503、`DataError` → 500、`LLMError` → 502、`RerankError` → 502、`EngineNotReady` → 503、参数错误 → 422、未预期 → 500（不返回堆栈）。底层 `errors.py` 不认识 HTTP，状态码只在 `api/errors.py` 里。

**两点现实说明**：① 当前 `/ask` 实际只会产生 422/503/500 —— LLM 失败在 `qa/pipeline.py` 里被捕获成 200 + “（生成失败：…）”，rerank 失败降级成 200 + `degraded=true`，502 映射目前没有触发路径；② `citations` 用 `CitationOut`，`sources` 用 `SourceOut`，两者字段不同（阶段六真机 500 的成因）。

**测试边界**：`tests/test_api.py`（6 项，生命周期）与 `tests/test_api_routes.py`（32 项，校验/响应/错误/并发/引用形状）用 FakeEngine，证明的是**接口行为与生命周期**，不是真实 RAG 质量。真实数据 + 真实 LLM 的 HTTP 端到端已于 2026-11-22 阶段六跑通（Q04 有答案、N01 拒答、`/readyz` 初始化、关闭时 `engine.close()`），但只有这一次、不是 15 题全量。

## 11. 一次真实问答，逐段看

```
问题：参数 3-22 和 3-23 是干什么的？
① 选策略：bm25
② 召回：30 个句子（含 "the gear ratio is set by the master scaling in parameter 3-22…"）
③ 回填：30 个父块，去重后 10 个 → 不用扩展
④ rerank：10 个里把 p11（定义句）排到第 1
⑤ 上下文：10 块，每块带 [Source n] + 页码
⑥ 生成：glm-4.5-flash 写出"3-22 分子 / 3-23 分母，用分数避免舍入误差"
⑦ 引用：[Source 2] → apply.pdf 第 11 页
⑧ 打印：过程 + 答案 + 来源
```

## 12. 出问题先看哪里（排错表）

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 报"缺少 ZHIPU_API_KEY" | `retrieval/store.py` 的 `api_key()` | 环境变量没设 |
| 检索结果全是目录页 | `retrieval/store.py` 的 `load_parents()` | 目录父块下没有句子，理论上不会出现；若出现说明数据被换过 |
| 交付不足 10 个 | `out/` 里没有，看 `trace` | 候选扩到 240 还不够，说明该问题确实没有 10 个相关块 |
| 答案说"文档中没有"但文档里有 | `qa_cases.json` 的 `pages` + `context` | 检索没命中，或 rerank 把相关块挤出前 10 |
| 引用页码对不上 | `qa/citation.py` 的映射 + `sources` | 模型写了不存在的编号，或上下文被截断 |
| rerank 报错但程序没停 | 打印里的 `⚠ rerank 已降级` | 额度/网络问题，已自动退回原顺序 |
| 中文问、英文文档答不上 | 策略 | BM25 倒排是英文 token，中文提问请用 hybrid |

## 13. 三个"为什么这样设计"

1. **为什么不把句子直接给 LLM？**
   句子太碎，表格行离开表头就没有意义（Q5 的 Control Word 表被切成 5 块，单块只有 bit 0–2）。父块是"能独立读懂"的最小单位。

2. **为什么 rerank 放在回填之后，而不是句子层？**
   因为最终要给 LLM 的是父块；在句子层重排还要再做一次去重，且句子分数无法代表整块的相关性。一次调用 30 个块，比 30 次调用句子便宜。

3. **为什么两种策略共用一个 `reranker.py` / `context_builder.py` / `generator.py`？**
   否则"两种方案的差异"里会混进"两套 Prompt 的差异"，实验就不可比了。**控制变量**是这套代码最值钱的地方。
